# Catvertising: AdMob setup and release handoff

The Store's **Your phone / Catvertising** unit contains a real native AdMob inline adaptive banner. It is part of the fictional phone, not a global banner. The request uses the measured billboard width and a 50-point maximum height, so compact iPad windows request a fitting ad size without scaling or clipping any returned creative. The creative is not overlaid with artwork, rewarded, or disguised as a game control. Go Indie removes advertising and retains the existing double offline earnings benefit.

## Required build

**Expo Go cannot display these ads. Rebuild the native development client.** Installing the JS package or restarting Metro is insufficient. This repo uses Expo 57, React Native 0.86 and `react-native-google-mobile-ads`; both Google ads and RevenueCat need native modules. Read against the [versioned Expo 57 documentation](https://docs.expo.dev/versions/v57.0.0/), plus the [wrapper's installation guide](https://docs.page/invertase/react-native-google-mobile-ads).

For local testing, set the existing `REVENUECAT_TEST_STORE_API_KEY`, then run `npx expo run:ios --device <udid> --port <free-port>`. Use a Debug build, or the EAS `development` / `ios-simulator` profile. Supported iOS EAS cloud Preview, TestFlight, and store builds are Release and require `REVENUECAT_IOS_API_KEY` plus real iOS AdMob IDs; the [README](../README.md#week-3-going-live-with-revenuecat) owns that key's environment and visibility contract. Simulators get test ads even with real units; register physical test devices in AdMob before testing real IDs. Never click live ads.

Production AdMob inventory is selected only when Expo config receives one of this repository's positive iOS release signals: local `run:ios --configuration Release`; Xcode's exact original `CONFIGURATION=Release`, captured before login-shell and `.xcode.env` sourcing; or the [EAS system markers](https://docs.expo.dev/eas/environment-variables/usage/#built-in-environment-variables) jointly reporting `EAS_BUILD=true`, `EAS_BUILD_RUNNER=eas-build`, `EAS_BUILD_PLATFORM=ios`, and `EAS_BUILD_PROFILE=preview` or `production`. An explicit local `--configuration Debug` overrides an ambient Xcode Release value. Every other evaluation selects sample inventory. In particular, `EAS_BUILD_RUNNER=local-build-plugin` is a developer-machine build, retains Google samples even under a production profile, and its native Release phase refuses to continue: live inventory in a non-store binary risks invalid traffic and AdMob account suspension, while EAS cloud is the supported release path. `expo start --no-dev` is refused because it would pair a production-mode JavaScript bundle with development inventory.

## Release safeguards — include in the PR description

The pinned banner callback path is `PhoneBillboard` → RN-GMA `BannerAd` / `BaseAd` → `RNGoogleMobileAdsBannerView`. JavaScript receives only the event type and payload, not a request token. On iOS, RN-GMA's delegate method still receives the originating `GADBannerView`, then discards that identity when it emits through the Fabric component view's current `_eventEmitter`. That native delegate dispatch is the earliest reliable request-identity boundary, before a recycled view can select its successor's JavaScript callback.

- Expo config carries iOS identifiers without validating them so non-iOS release configuration remains independent of `ADMOB_IOS_*`; the iOS-only guards below enforce them.
- The Expo safety plugin captures Xcode's original configuration before Expo Constants or the release guard enters a login shell, then both consumers share the same later `.xcode.env` layers without letting those layers relabel the build. For an Xcode Release, the native phase rejects missing, malformed, sample, cross-publisher, or archive-drifted iOS ID pairs. Thus a Debug prebuild archived as Release or a changed release ID pair fails loudly. Regenerate the iOS native project after changing IDs; do not manually edit generated native files.
- A local EAS Release intentionally embeds samples and is rejected by that native phase with cloud-build guidance. EAS cloud jobs require the exact `EAS_BUILD_RUNNER=eas-build` marker before production inventory can be selected; a missing or different runner never implies release.
- Dynamic Expo configuration refuses an iOS Release that lacks a usable RevenueCat iOS key before the bundle is produced; the [README](../README.md#week-3-going-live-with-revenuecat) owns the key contract. Development and simulator profiles may omit production credentials.
- A release JavaScript bundle validates its embedded iOS IDs at module import, even if a purchased user would hide the ad.
- There is no “allow test release” escape hatch. Debug/sample builds are for development only.
- Fabric banner callbacks are request-bound by the app-owned iOS boundary in [`native/ios/RPBannerRequestIdentity.m`](../native/ios/RPBannerRequestIdentity.m). RN-GMA 16.5.0 passes the originating `GADBannerView` to its delegate methods but otherwise forwards through the component view's current event emitter. The boundary compares that originating banner with the component view's current banner before RN-GMA can emit load, failure, open, close, impression, click, or app events. This prevents a delayed callback from a replaced banner from settling or obstructing its successor even when Fabric recycles the native component view. The config plugin copies and compiles this source during iOS prebuild; keep its native lifecycle regression and prebuild linkage tests when changing RN-GMA.
- **Known limitation:** UIKit can move an already-loaded banner beneath the dock fade before a coalesced React Native scroll event reaches JavaScript. The no-new-request-during-scroll contract depends on the required automatic-refresh setting above; with that prerequisite met, new requests remain blocked through drag and momentum until a settled event supplies a fresh viewport measurement, while the loaded creative stays mounted to avoid scroll flicker. JavaScript cannot synchronously close this native movement gap or override server-side SDK refresh; a durable visibility fix requires native-side occlusion enforcement.

## Entitlements and consent

Ownership is unknown until RevenueCat returns CustomerInfo; unknown, offline failures, Expo Go and missing keys do not authorize ads. On each configured launch, the app invalidates RevenueCat's persisted CustomerInfo cache and awaits its own explicit fetch before registering the identity-less update listener. That promise-held result catches a genuine refund at the next successful launch refresh and may downgrade confirmed ownership. Purchase, restore, and later explicit refresh results are likewise ordered by operation revision and may downgrade; confirmed CustomerInfo from purchase or restore updates entitlement state before returning, while a successful paywall result without a confirmed entitlement leaves ads disabled and ownership unresolved. Listener callbacks carry no causal operation identity: an active entitlement upgrades unknown or false ownership immediately, but a negative callback never revokes confirmed ownership, regardless of `requestDate`, delivery order, or quiescence. The accepted tradeoff is that a refunded owner can remain ad-free until the next successful launch refresh. Purchase confirmation also suppresses negative callbacks. Suppressed CustomerInfo cannot promote an unresolved persisted ownership flag to confirmed ownership. Delayed local hydration cannot replace freshly resolved ownership. Every valid saved away interval is reconciled through a fixed launch cutoff exactly once: base offline earnings are credited regardless of saved ownership, and the owner-rate remainder is added only when the saved state and current CustomerInfo both report active ownership. A fresh ownership confirmation records a durable rate boundary, so an open away interval keeps one minimum-duration check and one eight-hour cap while paying the base rate before confirmation and the owner rate only afterward. When current ownership is still unresolved, an eligible remainder becomes durable versioned owner-bonus debt. Confirmed ownership settles the debt into cash exactly once; confirmed non-ownership discards it. Either resolution persists a newer zero-amount tombstone so delayed hydration and repeated relaunches cannot restore or pay an older debt. The launch interval remains separate from the lifecycle clock: hydration never rewinds a later background or foreground timestamp, and a fresh confirmation advances lastSeen only when that clock has not already recorded a later away start, so already-ticked first-session foreground time cannot be repaid after relaunch.

UMP starts one shared consent-information refresh at each application launch before Mobile Ads initialization. Its public API cannot distinguish a prior consent record from a user who has never contacted UMP before initiating that refresh, so the launch attempt runs for every user, including Go Indie owners. Concurrent consumers share that attempt, and a successful update is reused for the rest of the launch. If it fails, only a later measured billboard visibility return for an eligible free user starts a replacement attempt; no timer or retry loop runs while the billboard is hidden or continuously visible. A player already known to own Go Indie never receives the automatic consent form or initializes Mobile Ads; the refresh only preserves a required privacy-options entry. If ownership is confirmed while consent or initialization is already in flight, that operation may finish before the post-operation ownership check suppresses the banner. This deliberate window never presents advertising to a confirmed owner. Errors and `canRequestAds=false` fail closed for ads. Changing privacy choices first removes the current banner and re-checks UMP state afterward.

The app is configured for a general audience. Debug and release builds call UMP without an under-age tag and do not set a Mobile Ads child-directed or age-restricted treatment. The app collects no age, requests no IDFA or tracking permission, and passes no purchase identity or custom targeting. Every banner request explicitly asks for non-personalized ads only.

With the required AdMob automatic-refresh setting disabled, a new banner request requires the entire measured billboard to be inside the ScrollView viewport and above the measured dock-fade boundary. Drag and momentum clear request authorization; only a settled final scroll event with a fresh confirming measurement restores it. The app cannot inspect or override that server-side setting, so keep Automatic refresh disabled as verified in AdMob on 2026-09-19. This request gate is not a complete presentation-visibility guarantee: an already-loaded banner follows the latest delivered visibility measurement and can briefly overlap the fade while native scrolling outruns JavaScript. The Store must also be active and foregrounded, with no notification, game/paywall overlay, or SDK-presented destination covering it. The destination-open barrier survives eligibility changes and banner unmounts; only an SDK `onAdClosed` callback or a measured background-to-active application return clears it. No successor banner is requestable while that barrier stands. An in-flight banner is retired when the presentation surface is lost. Once loaded, its native view remains mounted across temporary presentation changes but is concealed and interaction- and accessibility-disabled; it unmounts when eligibility is lost, privacy choices begin, an explicit load fails, or an expiry, size, or suspension-recovery replacement begins. Only a genuine no-fill response shows the fictional between-sponsors copy.
